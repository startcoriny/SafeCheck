# Incident 그룹핑 설계서

## 1. 목적

SafeCheck는 기사 중심 서비스가 아니라 사건(Incident) 중심 서비스를 지향한다.

동일한 사건을 여러 언론사가 반복적으로 보도하는 경우 사용자는 중복된 정보를 확인해야 하는 문제가 발생한다.

예를 들어 하나의 화재 사건이 뉴시스, 연합뉴스, 뉴스1, YTN 등 여러 언론사에서 동시에 보도될 수 있다.

사용자 입장에서는 동일한 사건을 여러 번 확인하는 것이므로 정보 탐색 비용이 증가한다.

따라서 SafeCheck는 동일 사건으로 판단되는 기사들을 하나의 Incident로 그룹화하여 사용자에게 제공한다.

초기 MVP에서는 문자열 기반 유사도 점수제를 사용하고, 고도화 단계에서는 의미 유사도 분석과 사건 단위 클러스터링을 적용한다.

---

## 2. 문제 정의

같은 사건을 여러 언론사가 서로 다른 표현으로 보도할 수 있다.

예시

기사 A

경기 광주 태전동 빌라 화재…주민 대피

기사 B

태전동서 불…20명 긴급 대피

기사 C

경기 광주 빌라 화재 발생

사용자는 세 기사가 서로 다른 사건인지 같은 사건인지 알기 어렵다.

SafeCheck는 이러한 기사들을 동일 사건으로 인식하고 하나의 Incident로 묶어 제공하는 것을 목표로 한다.

---

## 3. MVP Incident 그룹핑 방식

MVP 단계에서는 Python, 임베딩 모델, 벡터 DB를 사용하지 않고 TypeScript + NestJS 내부에서 문자열 기반 유사도 검증을 수행한다.

같은 사건 여부는 단일 유사도 알고리즘만으로 판단하지 않는다.

뉴스 제목은 언론사마다 표현 방식이 다르므로 후보군 제한, 제목 정규화, 문자열 유사도, TF-IDF 유사도, 규칙 점수를 함께 사용한다.

### 3-1. 사용 라이브러리

| 목적          | 라이브러리     | 사용 이유                                                 |
| ------------- | -------------- | --------------------------------------------------------- |
| 문자열 유사도 | talisman       | Jaro-Winkler, Levenshtein 등 fuzzy matching 알고리즘 사용 |
| TF-IDF / NLP  | natural        | 토큰화, TF-IDF, 문자열 유사도 계산                        |
| 토큰화        | wink-tokenizer | 뉴스 제목을 단어 단위로 분리                              |
| 후보군 검색   | fuse.js        | fuzzy search 및 weighted key 검색                         |

초기 MVP에서는 natural + talisman 조합을 우선 사용한다.

### 3-2. 처리 흐름

#### 1. 기사 단위 중복 제거

article_key 생성

NAVER:{pressCode}:{articleId}

예시

NAVER:003:0013976068

동일 article_key가 존재하면 동일 기사로 판단하고 저장하지 않는다.

---

#### 2. 후보군 제한

전체 기사끼리 비교하지 않고 먼저 비교 대상을 제한한다.

조건

- 동일 또는 인접 지역
- 동일 사건 유형
- 발행 시간 차이 3시간 이내

예시

서울 강남 화재

↓

서울 강남 화재

서울 서초 화재

비교

부산 해운대 화재

비교 제외

후보군을 먼저 제한하는 이유는 O(n²) 비교 비용을 줄이고 정확도를 높이기 위해서이다.

---

#### 3. 제목 정규화

언론사마다 표현 방식이 다르므로 비교 전에 제목을 정규화한다.

예시

불이 났다 → 화재

불길 → 화재

불남 → 화재

가스 샜다 → 가스누출

들이받아 → 충돌

차량 3대 잇따라 부딪혀 → 연쇄추돌

정규화 예시

경기 광주 태전동서 빌라 불…주민 대피

↓

경기 광주 태전동 빌라 화재 주민 대피

---

#### 4. 토큰화

정규화된 제목을 단어 단위로 분리한다.

처리 항목

- 특수문자 제거
- 괄호 제거
- 조사 제거
- 중복 공백 제거
- 의미 없는 단어 제거

예시

경기 광주 태전동 빌라 화재 주민 대피

↓

[경기, 광주, 태전동, 빌라, 화재, 주민, 대피]

---

#### 5. 유사도 계산

MVP에서는 다음 유사도를 함께 계산한다.

- Jaro-Winkler Similarity
- Token Jaccard Similarity
- TF-IDF Cosine Similarity

각 유사도의 역할은 다음과 같다.

| 기준          | 역할                  | 한계                           |
| ------------- | --------------------- | ------------------------------ |
| Jaro-Winkler  | 짧고 유사한 제목 비교 | 단어 순서 변경에 약함          |
| Token Jaccard | 공통 단어 비율 비교   | 의미가 같은 다른 표현에는 약함 |
| TF-IDF Cosine | 중요한 단어 중심 비교 | 데이터가 적으면 효과 제한      |

---

#### 6. 최종 점수 계산

같은 사건 여부는 하나의 유사도 기준으로 판단하지 않고 점수 기반으로 판단한다.

duplicate_score =

지역 일치 점수

- 사건 유형 일치 점수

- 시간 근접 점수

- Token Jaccard 점수

- Jaro-Winkler 점수

- TF-IDF Cosine 점수

세부 기준

| 항목          | 조건          | 점수 |
| ------------- | ------------- | ---- |
| 지역          | 동일 읍/면/동 | 30   |
| 지역          | 동일 시/군/구 | 20   |
| 지역          | 동일 시/도    | 10   |
| 사건 유형     | 동일          | 25   |
| 시간          | 1시간 이내    | 15   |
| 시간          | 3시간 이내    | 10   |
| Token Jaccard | 0.6 이상      | 10   |
| Token Jaccard | 0.4 이상      | 5    |
| Jaro-Winkler  | 0.88 이상     | 10   |
| Jaro-Winkler  | 0.80 이상     | 5    |
| TF-IDF Cosine | 0.7 이상      | 10   |
| TF-IDF Cosine | 0.5 이상      | 5    |

---

#### 7. 같은 사건 판단 기준

| 점수      | 판단      |
| --------- | --------- |
| 80점 이상 | 같은 사건 |
| 65~79점   | 유사 후보 |
| 64점 이하 | 다른 사건 |

---

#### 8. Incident 그룹 생성

같은 사건으로 판단된 기사들은 Incident 단위로 그룹화한다.

예시

Incident #100

강남역 흉기난동

관련 기사

- 뉴시스
- 연합뉴스
- 뉴스1

Incident에는 다음 정보를 저장한다.

| 항목                      | 설명                     |
| ------------------------- | ------------------------ |
| incident_id               | 사건 식별자              |
| article_count             | 관련 기사 수             |
| first_published_at        | 최초 기사 발행 시각      |
| latest_published_at       | 가장 최신 기사 발행 시각 |
| representative_article_id | 대표 기사                |
| risk_score                | 사건 위험도              |
| risk_level                | 사건 위험도 등급         |
| attention_score           | 관심도 점수              |
| attention_level           | 관심도 등급              |

article_count는 위험도 계산이 아니라 관심도 계산에 사용한다.

---

#### 9. 관심도(Attention) 계산

같은 사건을 여러 언론사가 반복적으로 보도하는 경우 사회적 관심도가 높을 가능성이 있다.

따라서 관련 기사 수를 기반으로 관심도 점수를 계산한다.

관심도 계산 기준

| 기사 수   | 관심도 점수 |
| --------- | ----------- |
| 1건       | 1           |
| 2~4건     | 2           |
| 5~9건     | 3           |
| 10건 이상 | 4           |

관심도 등급

| 점수 | 등급      |
| ---- | --------- |
| 1    | LOW       |
| 2    | MEDIUM    |
| 3    | HIGH      |
| 4    | VERY_HIGH |

관심도는 동일 사건을 몇 개의 언론사가 보도했는지 나타내는 지표이다.

위험도와는 별도로 계산한다.

---

#### 10. 대표 기사 선정

MVP에서는 가장 최신 기사를 대표 기사로 사용한다.

선정 기준

latest_published_at DESC

사건은 시간이 지나면서 추가 정보가 계속 보도되므로 일반적으로 가장 최신 기사가 가장 많은 정보를 포함하고 있다.

따라서 MVP에서는 복잡한 점수 계산 대신 최신 기사를 대표 기사로 사용한다.

---

### 3-3. 선택 이유

Jaro-Winkler만 사용하면 단어 순서가 바뀐 제목을 놓칠 수 있다.

Token Jaccard는 단어 순서가 달라도 공통 단어가 많으면 유사하게 판단할 수 있다.

TF-IDF Cosine은 "사고", "발생" 같은 일반 단어보다 "태전동", "가스누출", "빌라"처럼 사건을 구분하는 핵심 단어에 높은 가중치를 줄 수 있다.

또한 SafeCheck는 기사 서비스가 아니라 사건 중심 서비스이므로 같은 사건을 하나의 Incident로 묶어 관리하는 것이 사용자 경험 측면에서 유리하다.

위험도(Risk)와 관심도(Attention)를 분리함으로써 실제 위험한 사건과 단순히 많이 보도된 사건을 구분할 수 있다.

---

### 3-4. 한계

- 임베딩 기반 의미 유사도만큼 정확하지 않다.
- 지역명이 제목에 없으면 후보군 제한이 어려울 수 있다.
- 키워드 정규화 사전 품질에 영향을 받는다.
- threshold는 실제 수집 데이터를 기준으로 조정해야 한다.
- 같은 사건이라도 표현 차이가 매우 크면 다른 사건으로 판단될 수 있다.

---

### 3-5. 최종 판단

MVP에서는 TypeScript + NestJS 내부에서 natural, talisman 기반 문자열 유사도 검증을 수행한다.

같은 사건으로 판단된 기사들은 Incident 단위로 그룹화하고, 최신 기사를 대표 기사로 사용한다.

기사 수는 관심도(Attention) 계산에 사용하며, 위험도(Risk)와는 별도로 관리한다.

사용자에게는 기사 중심이 아니라 사건 중심으로 정보를 제공하는 것을 목표로 한다.

---

## 4. 고도화 Incident 그룹핑 방식

### 4-1. 고도화 목표

- 같은 사건을 더 높은 정확도로 탐지
- 언론사별 표현 차이 보정
- 사건 단위 그룹 자동 생성
- 대표 기사 자동 선정
- 사용자에게 중복 기사 대신 사건 단위 정보 제공

---

### 4-2. 처리 흐름

#### 1. MVP 유사도 기준 튜닝

운영 데이터를 기반으로 threshold를 조정한다.

#### 2. 사건 특징 추출 강화

- 시/도
- 시/군/구
- 읍/면/동
- 장소
- 사고 유형
- 피해 규모
- 인명 피해
- 시간 정보

추출 정확도를 높인다.

#### 3. 의미 유사도 분석

문자열이 아닌 문장의 의미를 비교한다.

예시

공동주택에서 화재 발생

=

빌라에 불이 나 주민 대피

---

#### 4. 사건 단위 클러스터링

기사 중심 구조를 Incident 중심 구조로 확장한다.

---

#### 5. 대표 기사 자동 선정

지역 구체성, 피해 정보, 사건 유형 명확성, 최신성, 언론사 신뢰도를 기반으로 대표 기사를 자동 선정한다.

---

#### 6. Incident 데이터 생성

같은 사건으로 판단된 기사들을 Incident 단위로 저장하고 관리한다.

---

### 4-3. 기대 효과

현재

기사 10건

↓

실제 사건 3건

↓

사용자는 10개의 기사를 확인

고도화 이후

사건 3건

↓

대표 기사 제공

↓

사용자는 핵심 사건만 확인

---

### 4-4. 트레이드오프

장점

- 중복 기사 노출 감소
- 같은 사건 탐지 정확도 향상
- 사용자 경험 개선
- 사건 중심 데이터 구조 확보

단점

- 구현 복잡도 증가
- 유사도 기준 튜닝 필요
- 오탐 및 미탐 검증 필요
- 운영 데이터 기반 지속적인 개선 필요

---

### 4-5. 최종 판단

초기 MVP에서는 문자열 기반 유사도 점수제를 사용한다.

이후 실제 수집 데이터를 통해 오탐 및 미탐 사례를 분석하고, 사건 특징 추출, 의미 유사도 분석, 사건 단위 클러스터링을 순차적으로 도입한다.

최종적으로는 기사 중심 구조가 아니라 Incident 중심 구조로 발전시키는 것을 목표로 한다.

---

## 5. 대표 기사 선정 정책

대표 기사는 단순히 가장 먼저 수집된 기사로 선택하지 않는다.

고도화 단계에서는 다음 기준으로 점수를 계산한다.

대표 기사 점수 =

지역 구체성 점수

- 피해 정보 점수

- 사건 유형 명확성 점수

- 최신성 점수

- 언론사 신뢰도 점수

예시 기준

| 기준                | 점수 |
| ------------------- | ---- |
| 읍/면/동 포함       | +3   |
| 시/군/구 포함       | +2   |
| 사망/부상/대피 포함 | +3   |
| 사건 유형 명확      | +2   |
| 제목 길이 15자 이상 | +1   |
| 더 최신 기사        | +1   |

대표 기사 교체 예시

기존 기사

경기 광주서 불

새 기사

경기 광주 태전동 빌라 화재…주민 20명 대피

새 기사가 지역, 장소, 피해 규모가 더 구체적이므로 대표 기사로 교체한다.

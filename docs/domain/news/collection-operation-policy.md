# 뉴스 수집 운영 정책서

## 1. 운영 정책 목적

뉴스 수집기는 외부 사이트 구조와 네트워크 상태에 영향을 받는다.

따라서 단순히 데이터를 가져오는 것뿐 아니라 다음 운영 기준이 필요하다.

- 수집 주기 관리
- 요청 횟수 제한
- 동시 실행 방지
- 실패 처리
- 재시도 처리
- HTML 구조 변경 감지
- 장시간 서버 중단 후 복구 정책
- 수집 로그 관리

---

## 2. 스케줄러 주기

| 수집 대상              | 갱신 특성                         | 최종 주기 |
| ---------------------- | --------------------------------- | --------- |
| 연합뉴스 재난·재해 API | 5분 주기 갱신                     | 5분       |
| 네이버 사건사고 수집   | 자체 갱신 주기 불명               | 기본 5분  |
| 긴급 모드              | HIGH 이상 감지                    | 3분       |
| 저부하 모드            | 신규 기사 없음 / 새벽 / 연속 실패 | 10분      |

---

## 3. 기본 수집 주기

기본 수집 주기는 5분으로 설정한다.

선택 이유:

- 실시간성을 어느 정도 확보할 수 있다.
- 하루 실행 횟수는 288회로 관리 가능한 수준이다.
- 요청량과 AWS 비용이 과하게 늘지 않는다.
- 외부 서비스에 불필요한 부하를 줄일 수 있다.
- 포트폴리오에서 운영 비용과 외부 서비스 부하를 고려한 설계로 설명할 수 있다.

트레이드오프:

- 실제 뉴스 반영과 SafeCheck 노출 사이에 최대 몇 분의 지연이 발생할 수 있다.
- 1분 단위 수집보다 실시간성은 낮다.
- 그러나 MVP에서는 안정성과 운영 비용을 우선한다.

---

## 4. 연합뉴스 API 호출 정책

연합뉴스 API가 5분 단위로 갱신되더라도 정각에 바로 호출하지 않는다.

예를 들어 다음 상황이 발생할 수 있다.

```
15:05:00 연합뉴스 갱신 시작
15:05:01 SafeCheck 조회
15:05:10 연합뉴스 데이터 반영 완료
```

이 경우 SafeCheck는 이전 데이터를 가져오고, 다음 조회는 15:10에 이루어져 결과적으로 5분 늦게 반영될 수 있다.

따라서 연합뉴스 API는 다음 방식으로 호출한다.

```
5분 주기 + 30~60초 지연 조회
```

예시:

```
15:05 갱신 대상
→ 15:05:40 조회
```

---

## 5. 네이버 사건사고 수집 호출 정책

네이버 사건사고 수집은 5분 주기로 실행하되, 매번 정확히 같은 시각에 호출하지 않는다.

호출 방식:

```
5분 주기 + 랜덤 지터
```

예시:

```
매 5분마다 정확히 호출하지 않고
5분 ± 30초 범위에서 실행
```

선택 이유:

- 외부 서비스에 일정한 패턴의 요청을 보내지 않는다.
- 특정 시각에 요청이 몰리는 것을 줄인다.
- 운영 안정성을 높인다.

---

## 6. 요청 제한 정책

네이버 사건사고 수집기는 다음 제한을 둔다.

| 항목               | 초기값     |
| ------------------ | ---------- |
| 최대 페이지 수     | 3페이지    |
| 최대 수집 건수     | 100건      |
| 최대 실행 시간     | 20초       |
| 재시도 횟수        | 1~2회      |
| 요청 간격          | 500ms ~ 1s |
| 스케줄러 기본 주기 | 5분        |
| 긴급 모드 주기     | 3분        |
| 저부하 모드 주기   | 10분       |

선택 이유:

- 외부 사이트에 과도한 요청을 보내지 않기 위해서이다.
- 서버 실행 시간이 길어지는 것을 막기 위해서이다.
- 스케줄러가 밀리는 것을 방지하기 위해서이다.
- 장애 상황에서 무한 반복을 막기 위해서이다.

트레이드오프:

- 장시간 서버가 중단된 뒤 재시작하면 일부 오래된 뉴스를 놓칠 수 있다.
- 최대 페이지 수를 늘리면 복구 가능성은 높아지지만 외부 요청 수와 처리 시간이 증가한다.
- MVP에서는 안정성을 우선하고, 수집 로그를 보면서 값을 조정한다.

---

## 7. 동시 실행 방지 정책

스케줄러가 5분마다 실행될 경우 이전 작업이 끝나기 전에 다음 작업이 시작될 수 있다.

예시:

```
15:00 수집 시작
15:05 아직 수집 중
15:05 다음 스케줄러 실행
```

이 경우 같은 데이터를 동시에 수집하려고 할 수 있다.

DB 유니크 제약으로 중복 저장은 막을 수 있지만, 불필요한 요청과 로그가 발생한다.

따라서 다음 정책을 적용한다.

```
동일 source에 대해 동시에 1개 수집 작업만 실행한다.
lock이 이미 존재하면 해당 회차 수집은 skip한다.
```

MVP에서는 DB 기반 lock을 사용한다.

## 8. 예외 처리 정책

### 네이버 응답 실패

처리 방식:

- 재시도 1~2회 수행
- 계속 실패하면 수집 실패 로그 저장
- 기존 데이터 제공 유지

서비스 영향:

- 실시간 수집은 실패하지만 기존 뉴스 목록은 계속 제공한다.
- 사용자 화면 전체 장애로 전파하지 않는다.

---

### HTML 구조 변경

처리 방식:

- 기사 목록 파싱 실패 시 실패 로그 저장
- 수집기 상태를 FAILED로 표시
- 관리자 확인 대상 로그로 남김
- 기존 데이터 제공 유지

서비스 영향:

- 신규 뉴스 수집은 중단될 수 있다.
- 기존에 수집된 뉴스는 계속 조회 가능하다.

---

### cursor 추출 실패

처리 방식:

- 최초 페이지 cursor 추출 실패 시 해당 회차 수집 중단
- 실패 로그 저장
- 다음 스케줄러에서 재시도

서비스 영향:

- 해당 회차 신규 뉴스 수집 실패
- 기존 데이터 제공 유지

---

### 중복 기사 과다

처리 방식:

- 기존 기사 발견 시 즉시 종료
- 유니크 인덱스로 중복 저장 방지

서비스 영향:

- 불필요한 더보기 요청을 줄일 수 있다.
- 신규 기사만 저장한다.

---

### 장시간 서버 중단 후 재시작

처리 방식:

- 1페이지에서 기존 기사를 못 만날 수 있으므로 최대 페이지 수까지 탐색
- 그래도 기존 기사를 못 만나면 최대 수집 건수 기준으로 제한
- 필요 시 전일 날짜까지 보완 수집

서비스 영향:

- 일부 오래된 뉴스가 누락될 수 있다.
- 무한 수집을 방지하기 위해 최대 페이지 수와 최대 수집 건수를 우선한다.

---

## 9. 수집 로그 정책

수집기는 매 실행마다 결과를 로그로 저장한다.

저장 항목:

- 수집 출처
- 수집 대상 날짜
- 시작 시각
- 종료 시각
- 요청 페이지 수
- 파싱 기사 수
- 신규 저장 기사 수
- 중복 기사 수
- 필터링 통과 기사 수
- 실패 여부
- 실패 사유

수집 로그 활용 목적:

- 스케줄러 정상 실행 여부 확인
- 수집 실패 원인 추적
- 외부 HTML 구조 변경 감지
- 신규 기사 수 급증/급감 확인
- 운영 지표 확인

---

## 10. 보관 기간 정책

실시간 뉴스 정보의 핵심은 최신성이다.

따라서 오래된 뉴스 데이터를 무제한 저장하지 않는다.

초기 정책:

```
노출 대상 뉴스: 최근 7일
DB 보관 기간: 30일
수집 로그 보관 기간: 90일
```

선택 이유:

- 사용자는 주로 현재 또는 최근 사고 정보를 확인한다.
- 오래된 뉴스가 계속 쌓이면 조회 성능과 저장 비용에 영향을 줄 수 있다.
- 수집 로그는 장애 분석을 위해 뉴스 데이터보다 오래 보관한다.

고도화 방향:

- 통계 기능이 필요해지면 오래된 뉴스는 별도 archive 테이블로 이동한다.
- 위험도 HIGH 이상 뉴스는 더 오래 보관할 수 있다.

---

## 11. 장애 대응 원칙

뉴스 수집 실패가 SafeCheck 전체 장애로 이어지면 안 된다.

따라서 다음 원칙을 적용한다.

```
외부 수집 실패 ≠ 사용자 서비스 전체 장애
```

장애 상황별 대응:

| 상황               | 사용자 화면                          |
| ------------------ | ------------------------------------ |
| 신규 수집 실패     | 기존 뉴스 목록 제공                  |
| 네이버 구조 변경   | 기존 뉴스 목록 제공 + 수집 실패 로그 |
| 연합뉴스 API 실패  | 네이버 뉴스 기반 데이터 제공         |
| DB 조회 실패       | 에러 응답                            |
| 키워드 필터링 실패 | 해당 기사 분석 실패 처리             |

---

## 12. 최종 운영 방향

SafeCheck의 실시간 뉴스 수집은 최신성, 안정성, 외부 서비스 부하, 운영 비용을 함께 고려한다.

초기 MVP에서는 다음 기준으로 운영한다.

- 5분 주기 수집
- 네이버 수집은 랜덤 지터 적용
- 최대 페이지 수 3페이지
- 최대 수집 건수 100건
- 최대 실행 시간 20초
- DB 기반 수집 lock 적용
- 수집 로그 저장
- 기존 기사 발견 시 즉시 종료
- 본문과 이미지는 저장하지 않음
- 기존 데이터 제공을 우선하여 수집 실패가 사용자 화면 전체 장애로 이어지지 않도록 처리

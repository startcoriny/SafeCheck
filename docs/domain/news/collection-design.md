# 네이버 사건사고 뉴스 수집 설계서

## 1. 문제 정의

SafeCheck에서 재난·재해 데이터는 공공 API 또는 연합뉴스 오픈 API를 통해 수집할 수 있다.

하지만 다음과 같은 사건사고성 정보는 일반 재난 API에서 충분히 제공되지 않는다.

- 칼부림
- 흉기난동
- 도시 추돌 사고
- 가스 누출
- 폭발
- 붕괴
- 대형 교통사고
- 지하철 사고
- 시설물 사고

이러한 정보는 사용자의 안전과 직접적으로 연결될 수 있으므로 뉴스 기반 수집이 필요하다.

---

## 2. 기존 방식의 문제

단순 크롤링 방식은 다음과 같은 흐름을 가진다.

```
네이버 접속
→ 뉴스 접속
→ 사회 섹션 접속
→ 사건사고 섹션 접속
→ 날짜순 조회
→ 더보기 반복 클릭
→ 전체 뉴스 수집
→ 키워드 필터링
```

이 방식은 다음 문제가 있다.

- 5분마다 전체 데이터를 다시 조회하게 된다.
- 이미 수집한 기사까지 반복 확인하게 된다.
- 시간이 지날수록 더보기 요청 횟수가 증가한다.
- 네이버 서버와 SafeCheck 서버 양쪽에 불필요한 부하가 생긴다.
- 중복 제거 비용이 증가한다.
- 브라우저 자동화 방식 사용 시 속도와 운영 안정성이 낮아진다.

따라서 전체 페이지를 반복 조회하는 방식은 사용하지 않는다.

---

## 3. 최종 선택 방식

최종적으로 네이버 뉴스의 사회 > 사건사고 섹션에서 사용하는 더보기 요청 구조를 직접 호출하는 방식을 사용한다.

브라우저에서 더보기 버튼을 클릭하면 다음 경로가 호출된다.

```
/section/template/SECTION_ARTICLE_LIST_FOR_LATEST
```

이 요청은 기사 목록을 HTML 조각 형태로 반환하며, 다음 페이지 조회를 위한 cursor 정보를 함께 제공한다.

따라서 수집기는 브라우저를 실행하지 않고, HTTP 요청을 통해 더보기 요청을 직접 호출한다.

---

## 4. 수집 대상

수집 대상은 네이버 뉴스의 사회 > 사건사고 섹션이다.

기본 URL:

```
https://news.naver.com/breakingnews/section/102/249
```

섹션 정보:

| 값       | 설명     |
| -------- | -------- |
| sid=102  | 사회     |
| sid2=249 | 사건사고 |

수집 목적은 뉴스 전문 제공이 아니라 사건사고 발생 여부 탐지이다.

따라서 기사 본문 전체와 이미지는 저장하지 않는다.

저장 대상은 다음 항목으로 제한한다.

- 기사 제목
- 기사 URL
- 언론사
- 발행 시간
- 네이버 기사 ID
- 언론사 코드
- 사건사고 유형
- 지역 정보
- 위험도
- 수집 시각

---

## 5. Cursor 기반 증분 수집 방식

네이버 사건사고 섹션은 단순 page 기반이 아니라 cursor 기반 더보기 구조를 사용한다.

최초 페이지에는 다음 cursor 값이 포함된다.

```
data-cursor-name="next"
data-cursor="2026052915312374026"
```

이 값은 첫 번째 더보기 요청의 `next` 파라미터로 사용된다.

첫 번째 더보기 요청 예시는 다음과 같다.

```
https://news.naver.com/section/template/SECTION_ARTICLE_LIST_FOR_LATEST?sid=102&sid2=249&cluid=&pageNo=1&date=&next=2026052915312374026&_=1780039665892
```

더보기 응답 이후에는 다음 cursor 정보가 `data-persist-meta`에 포함된다.

```
data-persist-meta="{&quot;cursor&quot;:&quot;2026052914461149877&quot;,&quot;has-next&quot;:true,&quot;page-no&quot;:2}"
```

이를 파싱하면 다음과 같다.

```
{
  "cursor":"2026052914461149877",
  "has-next":true,
  "page-no":2
}
```

다음 요청에서는 이 값을 사용한다.

```
pageNo=2
next=2026052914461149877
```

즉, 수집기는 cursor 값을 따라가며 다음 데이터를 가져온다.

---

## 6. 상세 수집 절차

### 1단계. 최초 사건사고 페이지 요청

수집기는 먼저 KST 기준 수집 대상 날짜의 네이버 사건사고 섹션 HTML을 요청한다.

요청 URL 형식:

```
https://news.naver.com/breakingnews/section/102/249?date={YYYYMMDD}
```

예시:

```
https://news.naver.com/breakingnews/section/102/249?date=20260529
```

이 HTML에서 첫 번째 더보기 요청에 사용할 cursor 값을 추출한다.

추출 대상:

```
data-cursor-name="next"
data-cursor
```

수집기는 실행 시점의 KST 기준 날짜를 사용한다.

단, 서버가 장시간 중단된 뒤 재시작되는 경우 전일 데이터 일부까지 보완 수집할 수 있다.

---

### 2단계. 기사 목록 파싱

최초 HTML에 포함된 기사 목록을 파싱한다.

각 기사에서 다음 값을 추출한다.

- 제목
- 기사 URL
- 언론사
- 발행 시간
- 기사 ID
- 언론사 코드

기사 URL 예시:

```
https://n.news.naver.com/article/003/0013976068
```

이 경우 고유키는 다음과 같이 생성한다.

```
NAVER:003:0013976068
```

---

### 3단계. 중복 여부 확인

각 기사별로 생성한 고유키를 DB에서 확인한다.

이미 DB에 존재하는 고유키를 만나면 해당 지점 이후의 기사는 이전 수집에서 이미 처리된 데이터로 판단한다.

이 경우 더보기 요청을 중단한다.

예시:

```
신규 기사 A
신규 기사 B
신규 기사 C
기존 기사 D 발견
기존 기사 E
기존 기사 F
```

이 경우 A, B, C만 저장하고 D를 만나는 순간 수집을 종료한다.

---

### 4단계. 더보기 요청 호출

최초 페이지에서 기존 기사를 만나지 못했거나, 더 많은 신규 데이터가 필요하면 더보기 요청을 호출한다.

호출 URL:

```
https://news.naver.com/section/template/SECTION_ARTICLE_LIST_FOR_LATEST
```

사용 파라미터:

| 파라미터 | 설명                  |
| -------- | --------------------- |
| sid      | 사회 섹션 코드        |
| sid2     | 사건사고 섹션 코드    |
| cluid    | 기본 빈 값            |
| pageNo   | 현재 페이지 번호      |
| date     | 조회 날짜             |
| next     | cursor 값             |
| \_       | 캐시 방지용 timestamp |

`_` 값은 캐시 방지를 위한 timestamp로 현재 시간을 사용한다.

---

### 5단계. 응답 HTML 파싱

더보기 응답에서 기사 목록을 다시 파싱한다.

동시에 다음 cursor 정보를 추출한다.

추출 대상:

```
data-persist-meta
```

포함 정보:

- cursor
- has-next
- page-no

---

### 6단계. 반복 여부 판단

다음 조건 중 하나에 해당하면 수집을 종료한다.

- 이미 DB에 존재하는 기사 고유키를 발견한 경우
- `has-next=false`인 경우
- 최대 페이지 수에 도달한 경우
- 최대 수집 건수에 도달한 경우
- 최대 실행 시간을 초과한 경우
- 네이버 응답 구조가 예상과 다른 경우

---

## 7. 중복 제거 기준

중복 제거는 두 단계로 나눈다.

---

### 7-1. 기사 단위 중복 제거

기사 단위 중복 제거는 같은 네이버 기사가 여러 번 저장되지 않도록 막는 것이다.

cursor는 페이지 이동을 위한 값이므로 기사 자체의 식별자로 사용하지 않는다.

고유키 생성 기준:

```
NAVER:{pressCode}:{articleId}
```

예시:

```
기사 URL:
https://n.news.naver.com/article/003/0013976068

고유키:
NAVER:003:0013976068
```

DB에는 다음 유니크 제약을 설정한다.

```
UNIQUE(source, press_code, article_id)
```

이렇게 하면 서비스 로직에서 중복 체크가 누락되더라도 DB 레벨에서 중복 저장을 막을 수 있다.

---

### 7-2. 사건 단위 그룹핑

사건 단위 그룹핑은 서로 다른 언론사가 같은 사건을 보도한 경우 하나의 사건으로 묶는 것이다.

예를 들어 아래 두 기사는 서로 다른 기사이지만 같은 사건일 수 있다.

```
NAVER:003:0013976068
NAVER:001:0011112222
```

두 기사 모두 “경기 광주 태전동 빌라 화재”를 보도한다면 기사로는 2건이지만 사건으로는 1건이다.

초기 MVP에서는 기사 단위 중복 제거를 우선 적용한다.

사건 단위 그룹핑은 고도화 단계에서 적용한다.

---

## 8. 최종 선택 이유

이 방식은 전체 페이지를 매번 다시 수집하지 않고, 신규 기사만 확인하는 증분 수집 방식이다.

기존 전체 크롤링 방식보다 요청 수와 처리 시간이 줄어든다.

또한 Playwright나 Puppeteer처럼 브라우저를 직접 실행하지 않기 때문에 서버 자원을 적게 사용한다.

공식 네이버 뉴스 검색 API보다 사건사고 섹션에 직접 접근할 수 있어 오탐이 줄어든다.

---

## 9. 대안 비교

### 대안 1. 네이버 뉴스 검색 API

장점:

- 공식 API이다.
- JSON 응답이라 처리하기 쉽다.
- 호출 한도 관리가 가능하다.

단점:

- 날짜별 수집이 어렵다.
- 사건사고 카테고리를 직접 지정할 수 없다.
- 삼성화재, 화재보험 등 오탐이 많다.

판단:

보조 수집원으로는 사용할 수 있지만, 사건사고 최신 정보 수집의 메인 방식으로는 부족하다.

---

### 대안 2. 브라우저 자동화 크롤링

장점:

- 실제 사용자가 보는 화면과 동일하게 동작한다.
- 더보기 버튼 클릭을 그대로 재현할 수 있다.

단점:

- 서버 자원을 많이 사용한다.
- 속도가 느리다.
- 운영 중 장애 가능성이 높다.
- 5분 단위 스케줄러에 반복 적용하기 부담스럽다.

판단:

최후의 수단으로 둔다.

---

### 대안 3. 더보기 요청 직접 호출

장점:

- 브라우저 자동화보다 빠르다.
- 서버 자원을 적게 사용한다.
- 사건사고 섹션 데이터를 직접 가져올 수 있다.
- cursor 기반 증분 수집이 가능하다.
- 중복 데이터 수집을 줄일 수 있다.

단점:

- 공식 공개 API가 아니다.
- HTML 구조나 파라미터가 변경되면 수정이 필요하다.
- 이용 정책 검토가 필요하다.

판단:

MVP에서는 이 방식을 사건사고 뉴스 수집 방식으로 채택한다.

단, 기사 전문과 이미지는 저장하지 않고 제목, 링크, 메타데이터 중심으로 저장한다.

---

## 10. 이용 정책 및 저장 범위

본 방식은 외부 개발자용으로 공식 제공되는 API가 아니므로 운영 환경 적용 전 이용약관, robots.txt, 요청 빈도, 저장 범위에 대한 검토가 필요하다.

따라서 MVP 단계에서는 다음 원칙을 지킨다.

- 기사 본문 저장 안 함
- 기사 이미지 저장 안 함
- 제목, 링크, 언론사, 발행 시간 등 메타데이터 중심 저장
- 원문 확인은 기사 링크로 이동
- 과도한 요청 방지를 위해 수집 주기와 요청 횟수 제한
- HTML 구조 변경 시 서비스 전체 장애로 전파하지 않음

---

## 11. 최종 결론

SafeCheck의 사건사고 뉴스 수집은 네이버 사건사고 섹션의 더보기 요청을 직접 호출하는 cursor 기반 증분 수집 방식으로 구현한다.

이 방식은 매번 전체 데이터를 크롤링하는 방식보다 효율적이며, 브라우저 자동화보다 가볍고 빠르다.

수집기는 5분 단위로 실행되며, 신규 기사만 저장하고 이미 저장된 기사 고유키를 만나면 즉시 수집을 중단한다.

기사 전문과 이미지는 저장하지 않고, 제목·링크·언론사·발행시간·지역·사건유형·위험도만 저장한다.

이를 통해 재난 API에서 제공하지 않는 칼부림, 추돌 사고, 가스 누출, 폭발, 붕괴 등 사건사고 정보를 보완한다.
